# Definition of done (applies to every project)

"Done" is decided before the work starts, not argued after. Two levels, both written down up front, both checked at the end with evidence.

## 1. Project DoD: set once, at onboarding

Every project's `CLAUDE.md` has a `## Definition of done` section: the checks that apply to every change in that project. Write it when onboarding (new project: before the first feature; existing project: from the checks already in its CLAUDE.md and PR template). Each line names its enforcer (`rule-enforcers.md`) or says `advisory`.

Baseline (start from this, delete what does not apply, add what the project has):

- Builds, typechecks and lints clean; the project's test command passes (run under `test-run-protocol.md`).
- New behavior has a test that fails without the change; a bug fix has the regression test.
- Docs that describe the changed thing are updated in the same PR (README, `CHANGELOG.md`, `DECISIONS.md` for a decision, feature map, and the `ux/` or `data/` sets when they apply).
- PR body is generated by the project's script, with the audience (who sees it) and changelog filled.
- Nothing left half-wired: no dead flag, TODO without an Inbox line, debug output, or commented-out code.
- Evidence labelled (`evidence-labels.md`): each check is `verified`, `read-only`, `agent-reported` or `not run`, with a reason for every `not run`.

Add-ons by change type (include the ones the project has):

| Change touches | Also done only when |
|---|---|
| UI, style, font, image, bundle | Lighthouse before/after in the PR (`web-accessibility-and-lighthouse.md`); accessibility check; UX docs updated; seen in a browser at phone and desktop width |
| Schema, migration, access rules | Migration runs forward on a copy; rollback or expand/contract plan stated; `data/` docs updated; production run left to the owner (`production-access.md`) |
| API route | Auth and plan check on the route; error and empty cases tested; contract doc updated |
| New dependency | Package delta and the lower ladder rung in the PR (`dependency-selection.md`) |
| Anything with per-use cost | Cap or tier recorded in `FEATURE-PLAN.md` |
| Device-only behavior (push, install, back-swipe) | Tried on a real device, or listed as `not run` and not called done |
| Deploy or release | Smoke check of the live URL; rollback step known; owner approved the prod step |

## 2. Feature "Done when": set at the Ready gate

A feature is not `Ready` (`feature-planning.md`) until its `FEATURE-PLAN.md` row has a **Done when** field: 3 to 7 observable statements about what a user, an admin or a test can see. Rules for writing them:

- Observable and checkable by someone else: "a free user with 5 saved routines sees the upgrade prompt on the 6th", not "limits work".
- Include the unhappy paths that matter (empty, offline, failure, over the limit) and who does not see it (audience, tier).
- Say what is **not** part of done (out of scope for this card) so extras go to the Inbox.
- Name the evidence for each line: test name, spec file, screenshot, measurement, or "owner tries on device".
- Anything that cannot be checked before release gets a kill/keep measurement instead (`Kill criteria`).

Stories and tickets: acceptance criteria are the feature's Done when (`user-story-decomposition`); do not write a second list.

## 3. Closing a change

1. Before starting: restate the Done when and the project DoD in one short list; if a line is vague, fix it first (`ambiguity-gate`).
2. While building: new ideas go to the Inbox; a change in what done means is a change to the row, said out loud.
3. Before saying "done": walk the list line by line and report each as `verified`, `read-only`, `agent-reported` or `not run`. A line that is not `verified` is named as such, and the work is "ready for review with these gaps", not done.
4. Handoff and PR body carry the list forward (`session-handoff`); the Dev Tracker card moves to Handoff only with the list attached.
5. Done means merged and, where the DoD says so, released and smoke-checked. "Open PR" is not done; report PR and merge state exactly.

## 4. Changing the DoD

The project DoD changes through a PR to its `CLAUDE.md` with a line in `DECISIONS.md` and the reason (usually a defect that slipped through). A check that was missed twice gets an enforcer, not stronger wording.

## Enforcers

- PR template: a **Done** section with the Done when list and the DoD checkboxes (`commit-and-push/pr-kit/pull_request_template.md`).
- `FEATURE-PLAN.md`: a row with an empty Done when is not `Ready` (stage gate, advisory until a lint exists).
- Everything else is advisory; `session-handoff` and `audit-codebase` carry it into reports.
