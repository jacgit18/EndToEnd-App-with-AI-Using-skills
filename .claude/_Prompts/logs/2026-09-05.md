<result>## 1. Condition A — BASELINE answer (no skill)

**Short answer:** add a composite b-tree on `(customer_id, status, created_at DESC)`, then drop the now-redundant standalone `(customer_id)` index. Build it with `CREATE INDEX CONCURRENTLY`.

**Why that shape.** The query pins two columns with equality (`customer_id = $1`, `status = 'open'`) and then wants the rows in `created_at DESC` order, `LIMIT 20`. A composite b-tree serves that best when the equality columns come first and the ORDER BY column comes last:

- `customer_id` is highly selective — 1.5M distinct values over 30M rows is ~20 rows per value — so it leads. That's the column that actually narrows the scan.
- `status` next. On its own it's useless as a leading column (`'open'` is ~4% = ~1.2M rows; the planner would just seq-scan), but as the second equality column it lets the index skip straight to this customer's open orders.
- `created_at DESC` last. With both equalities pinned, the index is already in `created_at` order within that group, so the planner walks the first 20 entries and stops — no sort node, no scanning all of the customer's orders. I'd write it `DESC` to match the query exactly, though Postgres can also scan a plain `(… , created_at)` backward.

Today, your `(customer_id)` btree gets you the customer's rows (~20), but then Postgres has to filter `status='open'` and run a top-N sort. At 20 rows that's cheap — if this query is genuinely slow at 30M rows, either the per-customer row count is much higher than the average for the hot customers, statistics are stale, or the slowness is heap-fetch / buffer-miss cost. Worth capturing `EXPLAIN (ANALYZE, BUFFERS)` before and after so you're not guessing.

**Partial index alternative.** Since the query *always* filters `status = 'open'` and that's only 4% of the table, a partial index is attractive:

```sql
CREATE INDEX CONCURRENTLY idx_orders_open_cust_created
  ON orders (customer_id, created_at DESC)
  WHERE status = 'open';
```

It's ~1/25th the size, and inserts of non-open rows (most of them) don't touch it. Caveat: when `status` flips to/from `'open'`, the row enters or leaves the index (a write either way), and the Postgres planner will only use this index if the query's literal `WHERE status = 'open'` is visible to it — a `WHERE status = $1` bound to `'open'` at runtime will *not* match the partial predicate. Your query uses the literal, so you're fine. I'd lean toward this version given the 4% selectivity and the 4,000 inserts/min.

**Covering / INCLUDE.** You could add `INCLUDE (total_cents)` (the other three SELECT columns are already in the key or are the PK) to get an index-only scan. I would *not* do this by default here: at 4,000 inserts/min every insert writes the wider leaf page, and this query sorts `created_at DESC` — it hits the newest rows, which sit on pages the visibility map hasn't marked all-visible yet, so you'd still see `Heap Fetches &gt; 0` and get little of the benefit. Add it only if a measured plan shows heap fetches dominating.

**Write cost.** You have 3 indexes now (PK, `customer_id`, `created_at`). Adding the composite and dropping the standalone `customer_id` keeps you at 3, so insert cost is roughly flat. `status` is in the new index, so the 1–2 status updates per row's lifetime now each cost a delete+insert in this index and can't be a HOT update — negligible at that frequency.

**Redundancy.** Once `(customer_id, status, created_at)` exists, the standalone `(customer_id)` btree is a strict prefix of it — anything it served, the composite serves. Drop it (`DROP INDEX CONCURRENTLY`), after the new one is live and you've confirmed nothing regressed. Keep `(created_at)` — it serves global time-range queries the composite can't.

**Rollout.** `CREATE INDEX CONCURRENTLY` so you don't take an `ACCESS EXCLUSIVE` lock on a 30M-row hot table. It can't run inside a transaction block, does two passes so it's slower, and if it fails it leaves an `INVALID` index you must drop and retry. Do it in a lower-traffic window and watch replica lag.

**Then re-measure:** re-run `EXPLAIN (ANALYZE, BUFFERS)`; confirm an Index Scan on the new index, no Sort node, ~20 rows read, and the latency actually dropped.
