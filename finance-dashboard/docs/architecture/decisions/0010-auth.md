# ADR 0010 — Auth approach

- **Status:** Accepted
- **Date:** 2026-09-10
- **Deciders:** the owner
- **Derived via:** `Architecture/tech-decision-walkthrough`, decision 8 of the stack
  (load-bearing; `access-control-modeling` questions are near-degenerate — one actor, full
  access, no tenancy — so the decision is purely the mechanism)

## Context

Single user, credentials from environment config, no signup / reset / multi-user (scope).
**Public URL over HTTPS** — unauthenticated traffic and brute-force attempts will arrive.
React SPA + FastAPI REST API. Stated goal: learn how auth actually works. Backlog S1's
assumption of stateless JWT is reopened by this decision.

## Decision

**Server-side session + `HttpOnly` cookie.**

- Login (`POST /api/auth/login`) verifies email + password against configured values, then
  creates a random opaque session ID stored in a `sessions` table (Postgres) and sets it as an
  `HttpOnly; Secure; SameSite=Lax` cookie.
- Every request except `/health` and the login endpoint requires a valid, unexpired session.
- Logout deletes the session row. Session expiry is configurable; expired rows are cleaned up
  by the reconciliation/maintenance job or a simple periodic task.
- **The SPA and API are served under one origin** (FastAPI serves the built React static
  files, or a single reverse proxy fronts both under one domain) — avoids cross-site-cookie
  and CORS complexity.
- The configured password is stored as **`AUTH_PASSWORD_HASH`** (argon2 or bcrypt), not
  plaintext; login verifies against the hash.
- CSRF: `SameSite=Lax` covers most; a CSRF token on state-changing requests is added as
  belt-and-suspenders.

## Alternatives considered

- **Stateless JWT (Bearer token in `localStorage`)** — lost on *revocation* (valid until
  expiry; a stolen token can't be killed) and *XSS exposure* (any JavaScript can read
  `localStorage`, so any XSS steals the token). Its one real advantage — statelessness for
  horizontal scaling — is worth nothing at one user on one server. Refresh tokens would patch
  the expiry/UX tension but are out of scope (S1).
- **JWT in an `HttpOnly` cookie** — fixes the XSS-read problem but is then cookie-based auth
  that still can't revoke and still needs CSRF defense — "sessions with a signed blob instead
  of a session ID," where the session ID is simpler.
- **HTTP Basic Auth** — near-zero code, but sends credentials on every request and has no
  clean logout; conflicts with the learning goal.
- **Reverse-proxy / external auth (Authelia, Cloudflare Access)** — battle-tested, but moves
  the mechanism out of the app; you learn to configure a proxy, not how auth works.

## Consequences

- **Backlog S1 amended:** "signed JWT" → "server-side session + `HttpOnly` cookie"; `JWT_EXPIRE_MINUTES`
  → `SESSION_EXPIRE_MINUTES`; `AUTH_PASSWORD` → `AUTH_PASSWORD_HASH`. Recorded in `docs/spec.md`
  drift log; S1 text reworded at build time.
- A `sessions` table + its Alembic migration.
- **Forces into later ADRs:** login-endpoint **rate limiting** (public URL), and **HTTPS /
  Let's Encrypt** in the deployment (ADR-0011/0012) so `Secure` cookies work.
- Server holds session state — trivial at this scale; enables instant "log out everywhere".
- Learning surface: cookie flags, `SameSite`, CSRF, session lifecycle, password hashing.
- If the app ever needs multiple users or third-party API access, revisit (a real `users`
  table, and JWT may earn its place for machine-to-machine access) — a deliberate v2 change,
  out of scope now.
